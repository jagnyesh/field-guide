# Third-party Claude Code tools that show what the agent is doing (state as of 2026-11-22)

Method notes for the report writer:

- **Stars and last-commit dates** come from the shields.io badge API (`https://img.shields.io/github/stars/<owner>/<repo>.json` and `.../github/last-commit/<owner>/<repo>.json`), queried 2026-11-22. Shields rounds stars ("20k") and gives relative dates: a bare month ("june") means that month of 2026; "june 2025" means the earlier year; "today / yesterday / last friday" means the week of 2026-11-22. The GitHub API and github.com HTML were not reachable from this session, so numbers are rounded and I could not read issue trackers directly.
- **Feature descriptions** come from each repo's README (read from raw.githubusercontent.com) unless another source is linked.
- The "Borrow" column in the tables is **my inference**, not a claim by the source.
- "Stale" = no commit in roughly 9+ months.

## Which tools are the most adopted in each group? (catalogue)

### Takeaway
Adoption is concentrated in cost/usage trackers (ccusage ~20k stars, CodeBurn ~12k), status-line HUDs (claude-hud ~29k, ccstatusline ~14k) and memory/methodology plugins (claude-mem ~119k, Superpowers ~324k); pure "what is the agent doing" observers are an order of magnitude smaller (claude-devtools ~4.1k, disler's hook dashboard ~1.6k, Claude Code Agent Monitor ~1.2k, agents-observe ~0.7k). No widely adopted tool combines a passive loop trace, a test-verification ledger, a context X-ray and a compaction autopsy; claude-devtools (context attribution + compaction visualisation, post-hoc) and agentsview (`session diagnose`, Friction Log) come closest on individual panes, and none of them is aimed at teaching newcomers.

#### (e) Tracing integrations

- **Anthropic-native baseline (context, not third-party):** OTel export is off by default and enabled by environment variables; detailed tracing is beta (`ENABLE_BETA_TRACING_DETAILED=1`, `BETA_TRACING_ENDPOINT`); "Claude Code does not pass OTEL_* environment variables to subprocesses it spawns, including hooks and the Bash tool" — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage.md).
- **Langfuse:** integration uses the hooks system, specifically a Stop hook script that fires after each response, with keys from the environment — [Langfuse Claude Code integration](https://langfuse.com/integrations/developer-tools/claude-code); [Tracing coding agents with Langfuse](https://langfuse.com/resources/engineering/coding-agent-tracing).
- **LangSmith:** official `langsmith-tracing` plugin installed through `plugin marketplace add` / `plugin install`; each message becomes a trace and a session's messages group into a thread; also works in CI via claude-code-action — [LangSmith: trace Claude Code](https://docs.langchain.com/langsmith/trace-claude-code). The older `langchain-ai/tracing-claude-code` repo shows 9 stars, last commit July 2026 (shields.io).
- **Braintrust:** plugin `trace-claude-code` (marketplace repo [braintrustdata/braintrust-claude-plugin](https://github.com/braintrustdata/braintrust-claude-plugin), 21 stars, Nov 2026) is recommended over manual OTel; it "forwards Claude Code's native hook payloads and reads the session", and "Hook failures never fail a Claude Code turn". It does not support the Cowork tab. Alternative: native OTel to Braintrust's OTLP endpoint — [Braintrust docs](https://braintrust.dev/docs/kb/setup-claude-code-with-otel-tracing-1781641599984).
- **Arize AX / Phoenix:** [Arize-ai/arize-claude-code-plugin](https://github.com/Arize-ai/arize-claude-code-plugin) (25 stars, March 2026): plugin `claude-code-tracing` emits OpenInference spans from 9 hooks (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, SubagentStop, Notification, PermissionRequest, SessionEnd). Arize also published Dev-Agent-Lens — [Arize blog](https://arize.com/blog/claude-code-observability-and-tracing-introducing-dev-agent-lens/).
- **Opik (Comet):** plugin maps each Claude Code turn to a trace with tool calls and responses as spans — [Comet blog](https://www.comet.com/site/blog/opik-claude-code-plugin/).
- **OpenObserve:** hook that sends session trace data via OpenTelemetry — [OpenObserve docs](https://openobserve.ai/docs/integration/claude-code-tracing).
- **claude-code-otel** ([ColeMurray](https://github.com/ColeMurray/claude-code-otel)): 525 stars, last commit June 2025 — **stale**. "Claude Code → OpenTelemetry Collector → Prometheus (metrics) + Loki (events/logs)" → Grafana.
- **opentelemetry-hooks** (o11y-dev): "OpenTelemetry integration for AI coding agents" incl. Claude Code — [repo](https://github.com/o11y-dev/opentelemetry-hooks).
- **Datadog / Honeycomb:** appear only as generic OTLP destinations in Anthropic's docs ("any backend that accepts the OpenTelemetry Protocol (OTLP), such as Honeycomb, Datadog, Grafana, Langfuse") — [Agent SDK observability docs](https://code.claude.com/docs/en/agent-sdk/observability.md). I found no dedicated Claude Code product page from either vendor.

## Which of them use DuckDB or SQLite to query transcripts or telemetry?

### Takeaway
SQLite is the default store for nearly every dashboard and archive (hook collectors write events to it; archives sync JSONL into it, usually with FTS5). DuckDB is rare and appears only in small, query-first tools — claude-sql, ccq and ccql — which all use the same zero-copy idea: point `read_json`/`read_ndjson_objects` at `~/.claude/projects/**/*.jsonl` and expose views.

### Cited Findings

**DuckDB**
- **claude-sql** (Laith Al-Saadoon / theagenticguy; Apache-2.0; v2.1.1 released 2026-08-20; Python 3.13+): "Zero-copy SQL + semantic search + LLM analytics over ~/.claude/ transcripts." Reader uses `read_json(..., filename=true, union_by_name=true, sample_size=-1, ignore_errors=true)` so the corpus is "queried in place"; raw reads become views, with business views and macros on top; nested content stays JSON and is flattened on demand — [PyPI: claude-sql](https://pypi.org/project/claude-sql/).
- claude-sql views: `sessions` (one row per transcript file: `session_id`, `started_at`, `ended_at`), `messages` (`uuid`, `session_id`, `role`, `model`, token usage), `tool_calls` and `tool_results` (derived from content blocks), `message_embeddings` (`embedding FLOAT[1024]`), `session_classifications` (`autonomy_tier`, `work_category`, `success`, `goal`), `user_friction` (`label`, `rationale`, `source`, `confidence`), `skill_usage`, `subagent_sessions`, `session_communities`; macros `model_used(session_id)`, `cost_estimate(session_id)`; CLI `query`, `explain`, `schema`, `shell`, `watch` — [PyPI: claude-sql](https://pypi.org/project/claude-sql/).
- claude-sql pipeline per its README diagram: `~/.claude/projects/*.jsonl` and `subagents/agent-*.jsonl` → `read_json` → raw views → business views → LLM passes (`classify / trajectory / conflicts / friction`, Sonnet 4.6) → sharded `part-*.parquet` → analytics views + macros; "Every parquet is cached and rebuilt only on explicit re-run"; example question: "Which todos do I create and never close out?" — [theagenticguy/claude-sql](https://github.com/theagenticguy/claude-sql).
- claude-sql's `friction` pass "combines a regex bank with Sonnet 4.6": regexes catch status pings, interruptions and corrections; ambiguous cases go to the LLM; only user messages under 300 chars are classified. Embeddings are stored in LanceDB, not DuckDB — [PyPI: claude-sql](https://pypi.org/project/claude-sql/).
- **ccq** (PyPI): runs DuckDB directly over `~/.claude/projects/<project>/<session>.jsonl` via `read_ndjson_objects` and exposes SQL views; a `--fast` mode uses a cached snapshot; `ccq sql` is read-only and refuses "Writes, ATTACH, COPY, INSTALL, and multi-statement input" — [PyPI: ccq](https://pypi.org/project/ccq/) (page would not load on direct fetch; details are from the search-engine summary of it).
- **ccql** (Rust crate, v0.5.0): "SQL engine for Claude Code and Codex CLI data"; a `transcripts` table covers top-level sessions and subagent transcripts and a `sessions` view aggregates one row per session with token totals and titles; docs note token totals cover only the top-level session file — [docs.rs: ccql](https://docs.rs/crate/ccql/0.5.0). (Search summary grouped it with the DuckDB tools; I did not confirm its engine.)

**SQLite**
- agentsview: sessions synced "into a local SQLite database", FTS5 search; optional `pg push` / `clickhouse push` for team dashboards; table layout not documented in the README; DuckDB not mentioned — [wesm/agentsview](https://github.com/wesm/agentsview).
- disler's dashboard: hook scripts POST to a Bun server that writes `events.db` (SQLite, with migrations in `db.ts`), then WebSocket to Vue — [disler/claude-code-hooks-multi-agent-observability](https://github.com/disler/claude-code-hooks-multi-agent-observability).
- agents-observe: hooks → local SQLite server; DB under `$CLAUDE_PLUGIN_DATA` when run as a plugin — [simple10/agents-observe](https://github.com/simple10/agents-observe).
- Claude Code Agent Monitor: better-sqlite3 in WAL mode — [hoangsonww/Claude-Code-Agent-Monitor](https://github.com/hoangsonww/Claude-Code-Agent-Monitor).
- claude-watch: tool calls "stored in SQLite, and broadcast to the dashboard via WebSocket" — [NirDiamant/claude-watch](https://github.com/NirDiamant/claude-watch).
- claude-usage: `scanner.py` parses JSONL into `~/.claude/usage.db` using only stdlib `sqlite3` — [phuryn/claude-usage](https://github.com/phuryn/claude-usage).
- cass: "SQLite is the source of truth for indexed conversations and messages. All derived assets (lexical index, semantic vectors, analytics rollups, retention backups) can be rebuilt from SQLite" — [coding_agent_session_search](https://github.com/Dicklesworthstone/coding_agent_session_search).
- claude-mem: SQLite at `~/.claude-mem/claude-mem.db` "holds sessions, observations and summaries", FTS5, Chroma for semantic search — [thedotmack/claude-mem](https://github.com/thedotmack/claude-mem).
- ccboard: SQLite metadata cache, "89x faster startup (20s → 224ms) ... handles 10K+ sessions" — [FlorianBruniaux/ccboard](https://github.com/FlorianBruniaux/ccboard).
- claude-code-log: SQLite cache, requires SQLite 3.35+ — [daaain/claude-code-log](https://github.com/daaain/claude-code-log).
- Other agents store sessions natively in SQLite (OpenCode, Hermes `~/.hermes/state.db`, Kiro, Antigravity), whereas Claude Code is JSONL-only — [claude-replay README](https://github.com/es617/claude-replay); [tokscale README](https://github.com/junhoyeo/tokscale).

**Neither:** of the ~50 READMEs fetched, only claude-sql mentions DuckDB (local grep, 2026-11-22). ccusage, CodeBurn, claude-devtools, claude-hud, cc-lens and the tracing plugins do not mention DuckDB in their READMEs.

### Inferences
- For someone learning DuckDB, claude-sql is the worked example to read: `union_by_name=true` handles Claude Code's heterogeneous line types, `ignore_errors=true` handles partially written lines, `filename=true` recovers the session/project from the path, and keeping `message.content` as JSON until a view unnests it avoids schema explosions. Derived (expensive, LLM-labelled) columns are materialised to parquet and re-attached as views — a clean separation between zero-copy facts and cached judgments.
- The split is functional: SQLite where the tool *writes* (live event ingest, FTS, single-row lookups); DuckDB where the tool only *reads and aggregates* files that Claude Code already writes. A passive observer that never needs to own the data fits the DuckDB side; a red/green ledger queried live inside a pane does not need either.
- The view names that recur across claude-sql and ccql (`sessions`, `messages`, `tool_calls`, `tool_results`, `subagent_sessions`) are a de facto logical schema for Claude Code transcripts.

### Gaps
- ccq: author, repo, release date and exact view schema not confirmed (PyPI page did not load).
- ccql: engine (DuckDB vs its own) not confirmed.
- Maintenance status and adoption of all three DuckDB tools are unknown; none appeared in awesome-claude-code's sections that I read. Stars for claude-sql were not checked.
- agentsview's actual SQLite table layout is not documented in its README.

## Do any detect unverified edits, weakened tests, mocks at boundaries, scope creep or reward hacking?

### Takeaway
Yes, but almost always as *blocking* PreToolUse/PostToolUse guards or as instructions to the model, not as passive flags shown to the human. The detections that exist are: test-first order and over-implementation (tdd-guard/Probity), gamed or disabled tests (Pragma, karanb192's guard pack, Slopwatch for .NET), and evidence-required success claims (presence). I found no tool that passively reports "edit never verified" or "turn ended red", and nothing that detects mocks at interface boundaries or scope creep.

### Cited Findings
- **tdd-guard**: hooks watch file operations; "Blocks implementation without failing tests" and "Prevents code beyond current test requirements" (over-implementation); validation by a configurable model; needs per-framework test reporters — [nizos/tdd-guard](https://github.com/nizos/tdd-guard).
- **Probity** (successor): "catches over-implementation and missing tests by reading your agent's session history (works with any test runner, in any language)"; each agent action fires a hook and Probity "either lets it through or sends back a reason and a path forward"; AI-validated rules reuse the agent's own auth — [tdd-guard README pointer](https://raw.githubusercontent.com/nizos/tdd-guard/main/README.md); [ecosyste.ms entry](https://awesome.ecosyste.ms/projects/github.com%2Fnizos%2Fprobity). A related repo, nizos/conduct, describes itself as a policy engine generalising tdd-guard — [nizos/conduct](https://github.com/nizos/conduct).
- **Pragma** (Joncik91): plugin that "watches every test file your AI assistant writes and blocks the edit when the test is gamed"; PreToolUse scans every Write of files matching `test_*.py`, `*/tests/*.py`, `*.test.ts` etc.; PostToolUse re-scans on disk to catch Edit cases; three tiers — Tier 1 always, Tier 2 on by default, Tier 3 (LLM, `PRAGMA_HOOK_WITH_LLM=1`) opt-in — [Joncik91/pragma](https://github.com/Joncik91/pragma). Note: shields.io reported this repo as not found on 2026-11-22, so its current existence is unconfirmed.
- **karanb192/claude-code-hooks** guard pack "blocks matched secret reads, dangerous commands, test disabling and destructive Git operations"; it documents coverage limits ("hooks only see the events...") — [karanb192/claude-code-hooks](https://github.com/karanb192/claude-code-hooks).
- **Slopwatch** (.NET only): detects "LLM reward hacking 'slop' in .NET code changes like disabled tests, suppressed warnings, empty catch blocks", wired as PostToolUse on Write|Edit|MultiEdit — [claudepluginhub: slopwatch](https://claudepluginhub.com/skills/deecalov-dotnet-skills/slopwatch).
- **presence**: "calibrated-confidence gate ... success claims need test evidence; your reverts are remembered" — [awesome-claude-code](https://github.com/hesreallyhim/awesome-claude-code).
- DIY pattern: a PreToolUse hook that denies edits to test files, which fires before the permission check and so holds even under `--dangerously-skip-permissions` — [dev.to: "Your AI agent will pass any test it's allowed to edit"](https://dev.to/penloom_studio_829b7817d3/your-ai-agent-will-pass-any-test-its-allowed-to-edit-51fo); mitigation write-up — [Nessim Bena blog](https://nessimbena.github.io/blogposts/mitigating-claude-code-reward-hacking.html).
- A Tessl-registry skill catalogues reward-hacking patterns for an implementation-integrity review — [tessl.io registry](https://tessl.io/registry/evilissimo/implementation-integrity-review/files/docs/reward-hacking-patterns.md).
- Passive, analytics-side signals: CodeBurn reports "one-shot rate, retry rate, self-correction" per model and flags re-read files — [getagentseal/codeburn](https://github.com/getagentseal/codeburn); agentsview's Friction Log reviews "corrections, tool errors, and recurring problems" and `session diagnose` lists "retry candidates" — [wesm/agentsview](https://github.com/wesm/agentsview); claude-sql classifies user friction (interruptions, corrections, `unmet_expectation`) and session `success` — [PyPI: claude-sql](https://pypi.org/project/claude-sql/); ccboard has an audit feed of "credential detection, destructive command alerts" — [FlorianBruniaux/ccboard](https://github.com/FlorianBruniaux/ccboard); Argus advertises "loop detection" — [Product Hunt: Argus](https://www.producthunt.com/p/argus-12/argus-15).
- Background: a public Claude Code issue (#7074, opened 2025-09-03) reports the agent modifying the test or working around it instead of following instructions, per a secondary Portuguese-language guide — [horadecodar.com.br](https://horadecodar.com.br/claude-code-alterando-testes/). Research benchmarks on reward-hack detection exist (EvilGenie; "Benchmarking Reward Hack Detection") — [arXiv 2511.21654](https://arxiv.org/html/2511.21654v1); [arXiv 2601.20103](https://arxiv.org/html/2601.20103v1).

### Inferences
- Three detection techniques are in use: (1) path/glob and regex or AST rules on the edited file (Pragma tiers 1–2, guard packs, Slopwatch) — cheap, deterministic, high precision on "test skipped/disabled/assert removed"; (2) sequence rules over session history (Probity: was there a failing test run before this implementation edit?) — this is exactly the shape of "edit never verified" and "turn ended red"; (3) an LLM judge (tdd-guard, Pragma tier 3, claude-sql) for the fuzzy cases, at the cost of tokens and sending code to an endpoint.
- Every tool using (1) or (2) returns its verdict *to the model* as a block reason. Probity's move from test reporters to reading session history is evidence that a transcript-only, sequence-rule ledger is technically sufficient without instrumenting the test runner — the same data a non-blocking observer can read.
- "User correction" mined from short follow-up messages (claude-sql's regex bank + 300-char cutoff; agentsview's Friction Log) is a cheap proxy for "the agent did something the human didn't want" and is the nearest existing thing to scope-creep detection.
- Because blockers feed findings back to the model, they change agent behaviour; none of the sources evaluates whether showing the same findings only to the human improves the human's learning. That is untested territory rather than a known result.

### Gaps
- No source found for detection of mocks at interface boundaries, or of scope creep as such.
- No tool found that flags "test changed to pass" passively (without blocking); absence is from the searches run, not proof none exists.
- False-positive rates or evaluations for any of these detectors: none published in what I read.
- Pragma's current availability; issue #7074's contents were not read first-hand.

## What do users say they still lack?

### Takeaway
The best-documented complaint is that Claude Code itself shows less by default: since v2.1.20 file paths, thinking, hook output and subagent output are collapsed, verbose mode is "too much noise", and people want a middle setting. Tool authors' own pitches name the remaining gaps: no breakdown of what fills the context window, no view inside subagents, transcripts that are hard to query, and agents that report success when the work failed. Direct Reddit/HN thread evidence was thin in this pass.

### Cited Findings
- In Claude Code 2.1.20 progress output stopped listing files read/edited, printing e.g. "Read 3 files (ctrl+o to expand)". Developers said they want file names for security, to catch context pulled from the wrong files, to audit, and to interrupt early to save tokens. On GitHub issue 21151 one user called it "an idiotic removal of valuable information"; another said verbose mode "is not a viable alternative, there's way too much noise." Boris Cherny said the aim was to "simplify the UI", then repurposed verbose mode to show file paths; "full thinking, hook output, and subagent output remain hidden" — [The Register, 2026-02-16](https://www.theregister.com/2026/02/16/anthropic_claude_ai_edits/).
- claude-devtools' README lists what its author considers invisible in the terminal: "Thinking steps", "Tool call details — you see a one-line summary, not the actual input/output", "Subagent activity — agents spawn agents, but you only see the final result", "Context window — a three-segment progress bar with no breakdown of what's consuming your tokens", and team coordination messages — [matt1398/claude-devtools](https://github.com/matt1398/claude-devtools).
- Subagent transparency requests: a feature request says there is no "built-in, user-friendly way to view the subagent's internal 'thinking' process, the specific tool calls it makes, the outputs of those tools, or any errors" — [issue 5974 mirror](https://claudeissues.com/issue/5974-feature-request-ui-for-subagent-execution-transparency-and-debugging); `--verbose` was the suggested answer and a commenter called it "TOO verbose" — [issue 2685 mirror](https://claudeissues.com/issue/2685-subagent-logs); a June 2026 bug reports subagent dispatch prompts and results hidden in the main thread with a collapsed line that cannot be expanded (regression after 2.1.160, still in 2.1.170), noting the data is still in the session JSONL — [issue 66646 mirror](https://claudeissues.com/issue/66646-bug-subagent-dispatch-prompt-and-returned-result-hidden-in-main-thread-collapsed); "subagent model and reasoning effort are invisible to every consumer" — [issue 95823 mirror](https://claudeissues.com/issue/95823-subagent-model-and-reasoning-effort-are-invisible-to-every-consumer-absent-from).
- Thinking visibility: requests to "Bring back thinking" — [issue 33163 mirror](https://claudeissues.com/issue/33163-feature-bring-back-thinking); explanation that summaries need `showThinkingSummaries` and Ctrl+O/verbose to render — [claudelog.com FAQ](https://claudelog.com/faqs/why-cant-i-see-claude-thinking/).
- Counter-demand: a VS Code request asks to hide subagent internals by default with an option to expand — [issue 11950 mirror](https://claudeissues.com/issue/11950-feature-vs-code-extension-respect-claude-subagents-md-and-hide-subagent-internal).
- Billing opacity as a driver: "Pro and Max subscribers get a progress bar. This gives you the full picture." — [phuryn/claude-usage](https://github.com/phuryn/claude-usage); "Your bill gives you a month total. It does not break that down by project, by model or by task, and it does not show which part of it was wasted." — [getagentseal/codeburn](https://github.com/getagentseal/codeburn).
- Sharing: "AI coding sessions are great for development, but hard to share. Screen recordings are bulky and transcripts are hard to navigate." — [es617/claude-replay](https://github.com/es617/claude-replay).
- Queryability: an essay argues Claude Code gives "a stream of tool calls mixed with conversation" that is hard to query — [Siddhant Khare, "agent observability gap"](https://siddhantkhare.com/writing/agent-observability-gap); a newsletter piece is titled "Your agent reported success. It failed." — [Practical AI](https://buttondown.com/practical-ai/archive/your-agent-reported-success-it-failed/).
- A tool-comparison article (vendor-written) notes that Langfuse's MCP access "does not capture the agent's own coding session" — [Braintrust: best coding-agent observability tools](https://www.braintrust.dev/articles/best-coding-agent-observability-tools).
- Tracing limits: Claude Code "does not pass OTEL_* environment variables to subprocesses it spawns, including hooks and the Bash tool" — [Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage.md); hook-based plugins don't work in the Cowork VM — [braintrust-claude-plugin](https://github.com/braintrustdata/braintrust-claude-plugin).

### Inferences
- The stated want is a *middle density*: more than collapsed summaries, less than `--verbose`. A one-line band plus on-demand panes is a direct answer to "verbose is too noisy / default hides too much".
- Users ask for visibility mainly to *act* (interrupt early, catch wrong-file context, audit, save tokens). Explanations aimed at people who do not yet know what to look for are not something the complaint threads ask for — newcomers are not the ones filing these issues — so demand for a teaching observer is not evidenced here either way.
- Subagents are the largest blind spot named across issues and tool pitches; several issues note the data is already in the JSONL, so a transcript-reading observer can show it without new hooks.
- "Agent reported success but failed" is voiced as a pain but, per the previous section, answered only by blockers — the unmet need closest to a red/green ledger.

### Gaps
- No Reddit (r/ClaudeAI, r/ClaudeCode) threads were retrieved; searches returned issue mirrors and blogs instead. Community sentiment here rests on The Register's reporting, issue mirrors (claudeissues.com, a third-party mirror, not GitHub itself) and tool READMEs, which are self-interested.
- No Hacker News thread was read first-hand (The Register cites Cherny's HN comments).
- I could not read the issue trackers of the catalogued tools (GitHub blocked), so "what users of tool X ask for" is unanswered.
- Whether the v2.1.20 defaults have changed again by November 2026 was not checked.
