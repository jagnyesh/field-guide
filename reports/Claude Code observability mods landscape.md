# Field Guide fills a gap nobody ships

Yes, both Anthropic and third parties ship tools that overlap with Field Guide, but none found in this research combines its four views with its stance, and the specific combination of a passive, in-session, rule-based observer whose findings never reach the model is unoccupied. Anthropic ships the raw facts as scattered, pull-based commands (`/context`, `/usage`, `/diff`, the transcript viewer), three sample mods, one built-in "You should know" note that costs a model call per check, and review plugins that all route findings back to Claude. Third parties cluster around cost trackers, status-line HUDs, transcript viewers and hook dashboards; the tools that judge process quality (tdd-guard, Probity, Pragma) do it by blocking the tool call and telling the model why. The closest neighbours on single panes are claude-devtools (context attribution and compaction, after the fact), agentsview (`session diagnose`), seedeep (live loop and context fill) and Devin's Session Insights (issue timeline). What they teach Field Guide is mostly about the next layer up: views of *what* is being built (change coupling, a data-layer timeline, playbook habits) and measures of *how* (time to green, rework), almost all of which can be computed from the paths, test ids, counts and timings Field Guide already keeps. Twelve of the proposals below fit the watch-only and metadata-only rules as written; the ones that do not fall into three decisions the maintainer would have to take: storage across sessions (out of scope in the PRD today), reducing file content to names or counts (ADR 0003), and anything needing a model call or a feed to the model (ADR 0001 and the README's promise). The single best fit for the DuckDB learning goal is not a pane at all: a metadata export that the requester queries with DuckDB offline.

## Anthropic ships the facts, never the interpretation

Anthropic's first-party surface is wide, and it is worth knowing in detail because Field Guide runs beside it. The table lists what overlaps; the "differs" column is measured against Field Guide's rules (watches only, no model call, findings never shown to the model, metadata only).

| First-party item | What it shows | How it differs from Field Guide |
|---|---|---|
| `token-weather` sample mod | A live "forecast" of the context window in the band above the prompt ([mods overview](https://code.claude.com/docs/en/plugins/mods/overview.md)) | One number as a metaphor; no breakdown of what fills the window |
| `replay-theater` sample mod | Steps through the last turn's file edits, one diff at a time ([sample mods](https://github.com/anthropics/claude-code-playground/tree/main/claude-code/mods)) | Edits only; no reads, runs or verification |

| `explanatory-output-style`, `learning-output-style` | Claude adds `Insight` blocks, or leaves `TODO(human)` code for the user to write ([output styles](https://code.claude.com/docs/en/output-styles.md)) | The model narrates itself; changes the system prompt and costs tokens every turn |

| Transcript viewer (`Ctrl+O`), `/focus`, task list (`Ctrl+T`) | The raw log; a one-line summary; Claude's own checklist | Raw or self-reported, with no grouping into loop steps and no flags |

| `/powerup` | Interactive lessons on Claude Code features | Teaches features in the abstract, not from the live session |
| OpenTelemetry export, analytics dashboards | Metrics, events and beta trace spans to a collector; adoption and ROI dashboards ([monitoring](https://code.claude.com/docs/en/monitoring-usage.md), [analytics](https://code.claude.com/docs/en/analytics.md)) | Fleet telemetry for an admin; needs a backend; teaches nothing |

Three facts in this list matter for positioning. First, Anthropic treats context visibility as the canonical mod: the overview's own example is "a pane that charts how full your context is after each request" ([mods overview](https://code.claude.com/docs/en/plugins/mods/overview.md)). A context band alone therefore looks ordinary; the Fixed load breakdown and the Compaction Autopsy go past what the samples show. Second, **Field Guide's flags restate Anthropic's own supervision guidance**. The best-practices page warns that without a check to run, "in practice that makes you the test suite", and says to "ask Claude for *evidence*: the command it ran and its output" because "'All tests pass' on its own tells you very little" ([best practices](https://code.claude.com/docs/en/best-practices.md)). The Red/Green Ledger shows that evidence without the user asking. Test changed to pass has no matching sentence in the pages read, so it is Field Guide's own contribution. Third, Anthropic's context advice has moved from scarcity to cost: with a 1M-token window on most current models "you'll rarely run out of context. You can still *pay* for context you don't need" ([best practices](https://code.claude.com/docs/en/best-practices.md)). An X-ray that teaches "what you re-send on every request" matches that; one that teaches "you are about to run out" is behind it.

The research did not find a mods launch date (only versions), did not read the three sample mods' READMEs, and could not confirm the Anthropic Academy course list. Absence of a first-party teaching observer is from the pages read, not proof that none exists.

Outside Claude Code, other agents have converged on a plan, a task list, a diff pane and a summary. The distinctive ones for this purpose are **Devin's Session Insights**, which lays out issues with impact ratings, a timeline with issue-linked events in bold, and action items for the user's setup ([Devin docs](https://docs.devin.ai/product-guides/session-insights)); Windsurf Codemaps, model-generated maps of how code connects ([Cognition](https://cognition.ai/blog/codemaps)); Kiro's specs, which link tasks to requirements ([Kiro docs](https://kiro.dev/docs/specs/)); Amp's suggested review order with churn indicators ([Amp](https://ampcode.com/news/review)); Copilot's `Agent-Logs-Url` commit trailer ([GitHub changelog](https://github.blog/changelog/2026-03-20-trace-any-copilot-coding-agent-commit-to-its-session-logs)); and Cursor's Agent Trace draft spec ([agent-trace.dev](https://agent-trace.dev/)). No surveyed product ships a per-session ledger tying each edit to a later verifying run, and none has a data-model view.

The pattern across all of this is that detection and delivery have been bundled. Every tool that detects a gamed test, a skipped test or a missing red step returns the verdict to the model as a block reason. Probity's move from per-framework test reporters to "reading your agent's session history" ([tdd-guard README](https://raw.githubusercontent.com/nizos/tdd-guard/main/README.md)) is independent evidence for ADR 0002: the transcript is enough to judge red and green order. What nobody has tested is whether showing the same findings only to the human improves the human's understanding. Research gives a reason to think the stance is sound without proving it: LLM monitors caught 86 to 89% of test cheating on one benchmark but only 42 to 65% on realistic repositories ([ImpossibleBench](https://arxiv.org/abs/2510.20270)), which favours deterministic rules worded as facts, and Anthropic's own trial found a 17-point quiz deficit for developers who learned a library with AI help, with the low scorers delegating and the high scorers asking follow-up questions ([Anthropic research](https://www.anthropic.com/research/AI-assistance-coding-skills)). Demand is less clear. The complaint threads ask for a middle density between collapsed summaries and `--verbose` ([The Register](https://www.theregister.com/2026/02/16/anthropic_claude_ai_edits/)), and subagents are the most-named blind spot, but those issues are filed by experienced users. Whether new developers want a teaching observer is not evidenced either way.

## Twelve additions fit the rules as written

The comparable tools point at a second layer for Field Guide. The v1 views answer "what is the agent doing"; the glossary already names the next subject, Codebase understanding, and defers it. Most of what follows builds that layer from data the timeline already holds. Priority weighs learning value against cost and against how exact the signal is. The tier column uses this repo's own risk tiers: a new pane over existing data is Medium, and anything that changes `lib/classify.ts`, `lib/metadata.ts` or `hooks/**` is High and needs a grill, a design note and an ADR first.

Two cautions apply across the table. Activity counts mislead on their own; the SPACE authors call activity the most misused measure ([GitHub summary](https://github.blog/news-insights/research/measuring-enterprise-developer-productivity/)), so every count should sit beside an outcome, edits beside time to green. And proposals 2, 3 and 5 are approximate where v1 is exact. The PRD kept codebase views out of v1 because "they rely on approximate signals", and the Shell edit labels (exact, best guess) are the precedent for how to show the difference.

## The DuckDB goal is best served outside the pane

For someone studying DuckDB, the richest material in this landscape is the session data itself, and the established pattern is to query it in place. claude-sql points `read_json` at the transcripts with `union_by_name=true` for the mixed line types, `ignore_errors=true` for half-written lines and `filename=true` to recover the session from the path, keeps nested content as JSON until a view flattens it, and caches expensive derived columns as Parquet ([claude-sql](https://pypi.org/project/claude-sql/)). Those four choices are a compact lesson in schema-on-read. DuckDB's own profiling output adds the second lesson: per-operator timing, rows scanned, and row groups scanned against row groups available, as JSON or as a Mermaid or HTML plan ([DuckDB profiling](https://duckdb.org/docs/2.0/dev/profiling.html), [metrics](https://duckdb.org/docs/2.0/dev/metrics.html)).

Embedding DuckDB in the mod is the wrong way to get there. The live views do not need an analytical engine, the tools that write events as they arrive use SQLite while the ones that only read and aggregate use DuckDB, and a native binding adds install weight and platform limits ([Node client](https://duckdb.org/docs/2.0/clients/node_neo/overview)). Two steps serve the goal better. The first needs no change to Field Guide's rules: a `docs/` page of DuckDB queries over the requester's own transcripts that use `read_ndjson_objects` and extract only identifiers, types and timestamps, so message text never becomes a column, with `EXPLAIN ANALYZE` exercises on each. That is Low tier. Transcript fields are not a stable interface, though: a published set of cost queries broke when `costUSD` left the JSONL after Claude Code 1.0.6 ([Zenn](https://zenn.dev/trysmr/articles/claude-max-duckdb)). The second step is the stronger one and needs a decision: a `/guide export` that writes Field Guide's own timeline (turns, steps, test runs, flags) as metadata-only files for DuckDB to read. Existing SQL tools all read message content, so a metadata-only dataset is a differentiator and not a copy. It also gives the systems-design goal a real exercise, designing a small schema, and the recurring view names in claude-sql and ccql (`sessions`, `messages`, `tool_calls`, `tool_results`) are a starting vocabulary.

## Three decisions gate the remaining ideas

Everything else worth borrowing runs into one of three lines the project has already drawn. Each deserves its own decision record, and under this repo's rules each is High tier.

| Decision | What it would unlock | Why it needs a decision | Assessment |
|---|---|---|---|
| **A. Keep metadata across sessions, and add an export file as a place metadata may go** | The DuckDB export; repo-level hotspots and coupling for the Change Map; a "stage evidence" strip (first CI config, first migration, first deploy command, with dates); a daily digest like agentsview's Friction Log; remembered flag mutes | The PRD lists "Storage across sessions" as out of scope, and ADR 0003 names the places metadata is copied to (state, store, toasts, status line, handed-off prompts, debug log). An export is a new one. The store already keeps compaction metadata for the last 20 sessions, so this widens a precedent | Take it first. It keeps both rules intact and unlocks the most learning. Session data is removed after 30 days by default ([costs](https://code.claude.com/docs/en/costs.md)), so a store is also what makes longer trends possible |
| **B. Read file content and keep only names, kinds or counts** | Dependency names added to a manifest (for a scope-drift meter and for "analytics added before first deploy"); DDL kinds per migration; a DuckDB plan card from a profiling JSON file, keeping operator types, timings and row-group counts and dropping `query.sql` and `operator.extra_info`; an error-class count for lock and transaction conflicts; an assertion-strength badge (none, executes only, checks values) after [arXiv 2606.18168](https://arxiv.org/html/2606.18168v1) | ADR 0003's strength is that "a reviewer can check the whole privacy story in one rule". Each reduction is a new kind of copied data that a reviewer has to trust. The plan card also reads the application's output, which the PRD rules out, and the PRD separately rules out "judging what an assertion means" | Take case by case. Dependency names and DDL kinds are low risk. The plan card is the most valuable for DuckDB learning and the furthest from the current rule; the offline notebook reaches the same lesson with no rule change |
| **C. Call a model, or let findings reach the model** | An end-of-session walkthrough like Antigravity's; a decision log mined from the agent's messages; Codemap-style explanations; "three things to understand before you continue"; an indicator of how the developer engaged (questions against pure delegation); an opt-in feed of flags to Claude | The README promises it "never calls a model"; the PRD dropped Intent Echo for needing one; ADR 0001 defers an opt-in feed to v2 and requires it off by default. The engagement indicator would also classify the developer's own prompts, and the research note warns it can feel like surveillance | Leave closed. Every comparable guard already feeds the model, so that ground is taken, and Field Guide's independence is its distinguishing property. Deterministic stand-ins fit today: a walkthrough skeleton from the Loop Trace (edits in order, each with its verifying run) and a decision timeline from `docs/adr/` paths and dates |

Two smaller items sit beside these. Writing a session link into commits, as Copilot's trailer and git-ai's notes do, would have Field Guide change the repository; marking in the Loop Trace which turns ended in a commit, as bough does, gives most of the lesson while only watching. And exporting spans to an OpenTelemetry backend sends data off the machine; matching the names (proposal 9) teaches the vocabulary without that.

## Conclusion

The landscape changes how Field Guide should describe itself more than what it should build next. Its context band is the least distinctive thing about it, since Anthropic uses exactly that as the tutorial mod. Its distinctive properties are that it detects what the blocking guards detect and declines to tell the model, and that a reviewer can verify the privacy claim by reading one rule. Trust is something users of this ecosystem have been taught to look for (claude-hud advertises a locked-down process), and `claude plugin validate` gives Field Guide a first-party way to prove it only observes. That is worth a line in the README.

One inconsistency surfaced while reading. The PRD maps views to stages named Build, Test, Maintain and Deploy, while the Founder's Playbook PDF defines four stages, Idea, MVP, Launch and Scale, and its exit criteria are business evidence such as retention and interviews that no session observer can see ([playbook PDF](https://assets.claude.com/503ee04b4aa55a4db49a69b993463b6fa8dad6d8.pdf)). The playbook also says almost nothing about testing technique, code review or deployment mechanics. Field Guide can honestly show the build-side habits the playbook prescribes and should say "evidence consistent with", never name a stage. The order that follows from all of this is the session measures and the Change Map first, because they are exact enough and cost only a pane; then decision A, because the DuckDB export turns the mod's own data into the requester's study material; and decision C not at all.
